## 确认问题与修复边界

原 `ExecuteStorageTransactionInternal()` 对前台和后台都执行
`new (std::nothrow) StorageCompletion()`。该对象内含静态二值信号量存储区、请求 ID、
结果和生命周期状态。前台允许排队超时后退出，确实需要独立于调用者栈的寿命；后台
始终等待，却也依赖这次动态分配。

三域包下载在错误后通过 `ExecuteStorageTransactionNamed(...Abort...)` 请求关闭 FILE
并清理临时文件。如果这次完成对象分配返回空，事务在入队前返回 NO_MEM，Abort
尚未运行；调用者继续结束下载，可能留下文件句柄及临时文件。这是明确的错误路径，
没有从正常设备日志推断已发生此故障，也不推断已丢失被接受的学习记录。

新增内部后台执行函数：

1. 在调用者栈中创建 StorageCompletion，用既有 CreateBinaryStatic 初始化信号量。
2. 发布 command 到后台队列，保留请求 ID 和原 esp_timer 排队起点，通知同一存储 owner。
3. 等待完成信号；若一次无限等待意外返回失败，保留两个栈对象并重试，不转换到
   Abandoned，不让 worker 引用已经失效的地址。
4. owner 通过原 Queued → Running → Done 流程执行、发布结果和给信号后，返回实际结果。

队列拒绝发生于 command 未发布时，允许立即返回；存储服务未启动、参数无效和 owner
重入仍走原门控。前台继续使用独立堆对象，保持 15 秒排队窗口、未运行可放弃、已运行
必须等待完成的契约；没有把 15 秒变成事务完成硬期限。

移除的是 **后台完成对象的动态分配依赖**。回调、NVS/SPIFFS、路径字符串及其他层仍
可能使用内存或失败，不能宣称所有 Abort 在任意资源耗尽时都必定完成。队列/静态信号量
初始化等异常仍返回原有错误类别。后台调用也没有新增整体完成期限。

没有新增 worker、持久化状态或固定全局池。存储任务优先级、20 KiB 栈、每笔事务后的
watchdog yield、容量阈值、临时文件租约、ADC/UI 时序和低电关机预算保持。

## 栈寿命、内存位置与资源

后台调用始终同步等待终态，因此 completion 和 command 的地址有效至 owner 不再
使用它们；前台排队放弃只操作其独立堆对象。worker 只有在看到 Abandoned 时释放
堆对象，后台不会发布该状态。没有将所有 completion 都放到栈上。

局部对象位于实际调用者栈，使用更多已分配栈空间。本候选编译器将后台 helper 内联到
`ExecuteStorageTransactionInternal`，入口帧为 **208 B**；这是单个静态帧大小，未包含
完整调用链、ISR 或实际高水位。未据此减少任务栈或声称设备栈已经验收。

若调用者使用 PSRAM 栈，该局部对象也可能在 PSRAM。本实现只由普通任务操作信号量；
本机 SDK 的 `docs/en/api-reference/system/freertos.rst` 的 FreeRTOS Heap 部分允许通过
CreateStatic API 放置外部内存对象。Flash/NVS 工作仍在原内部栈的 StorageService
执行，没有从调用者栈直接进入 Flash 驱动。主机测试不证明 cache-disabled/双核调度
窗口，设备矩阵保留 PSRAM 调用者与 Flash 并行场景。
