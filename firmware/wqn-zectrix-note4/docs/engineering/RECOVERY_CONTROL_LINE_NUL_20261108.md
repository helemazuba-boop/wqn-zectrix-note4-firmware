# R-08 恢复传输控制行 NUL 后缀（2026-11-08）

## 问题与证据

`EvidenceTransfer::Line` 把原始控制行写入 C 字符串，再用 strcmp/strlen/Unhex 匹配 READY、分组 ACK 和最终提交 ACK。
含合法控制字段、嵌入 NUL 及额外垃圾字节的整行，会在 NUL 处截短后被接受；这不表示任意 capture/hash 能通过，也不绕过设备端物理确认。
它破坏整行协议边界：坏 READY 可提前读取源介质，坏 ACK 可推进设备落盘进度，坏最终 ACK 可误报设备已确认提交。

验证基线 `f8414e6` 的原始生产传输源码，在实际导出 worker/transport/raw collector 加主机硬件端口下，新增测试共 188 检查出现 13 个行为失败。
数据、设备身份及介质均为合成样本；不是实机 USB 或真实数据读取。

## 修正与回归

遇到 NUL 将整行标为不可用，丢弃到下一个 LF，再从新行同步；不把截短前缀交给控制字段比较。
READY、分组 ACK、最终 ACK 各有持续注入场景，另覆盖坏 READY/ACK 一次后的完整重试。
最终 ACK 被拒绝时，电脑已经校验保存的完整原始镜像仍被保留；设备确认未知、未确认末窗口和传输不确定标记分别保留。

修正后 188/188 检查通过。仅移除 NUL 保护的行为负对照完整运行，恢复同样的 13 个失败；没有用编译错误、异常或超时充作检测成功。
完整两线门禁及零 warning SDK/M8/profile/UI 栈结果由当前批次 REPORT.md / receipt.json 保存。

## 主机等待控制器复核

综合门禁还复现夹具控制等待丢通知：原子标志在控制互斥锁外更新，通知可能先于 wait 发生，导致调用方等待整个看门狗窗口，另一线程先报夹具未能推进。
控制器仍保留 2 秒真实看门狗，改为最多 1 毫秒的有界重检。生产代码、虚拟存储期限和故障断言均未放宽。
新场景确定性地在首次谓词快照之后、wait 之前发布状态/通知；恢复整窗等待的负对照必须完整执行并因行为断言失败，不能把夹具 abort 计为通过。
