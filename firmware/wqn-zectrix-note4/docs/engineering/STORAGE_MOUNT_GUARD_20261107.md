# 存储启动挂载判定与 R-08 前置故障

## 已复现的错误与修正

ESP-IDF v5.5.6 的 `components/spiffs/esp_spiffs.c` 不仅在同名实例已经注册时返回
`ESP_ERR_INVALID_STATE`，也会在挂载槽耗尽、SPIFFS 分区被标记为加密时返回这个错误。
原 `InitStoragePartition()` 将所有该错误直接转换为成功，无法证明 `storage` 分区可用。

现在仅在 `esp_spiffs_mounted(kStoragePartitionLabel)` 为真时将其作为幂等成功；否则保留
SDK 错误，由 `InitStorage()` 传播到启动恢复入口。成功的初次挂载和真正已有的挂载仍然可用，
可选空间统计失败不撤销成功挂载。`format_if_mount_failed` 始终为 false。

`test_storage_mount_guard.py` 直接提取生产 C++ 函数，以 SDK API 端口模拟以下返回情形：
初次成功、目标已挂载、未挂载的 invalid-state、只有其他分区挂载、未找到、内存不足、
一般失败和可选统计失败。修复前 66 检查 / 5 失败；修复后 69 检查 / 0 失败。
移除目标挂载证明的负对照完整执行后恢复 66 检查 / 5 失败。不同数量来自额外执行的挂载标签断言。
这不是设备实际加密、挂载槽耗尽、文件系统或断电验收。

## R-08 导出入口的实际依赖

启动顺序是 `EnsureStorageSchema()` → `InitStorage()` → 业务启动。
schema 错误会在挂载 SPIFFS 之前进入恢复 UI；挂载错误同样可能留下未挂载状态。
现有 `CaptureStorageEvidenceOnOwner()` 则明确要求 `esp_spiffs_mounted("storage")`。
因此，只把逻辑采集器接到串口或恢复 UI，不能覆盖这些前置故障；不能为导出而调用
完整 `InitStorage()`、迁移或修复流程，把尚未保全的介质先改写。

后续完整设备导出必须同时满足：

1. 根据实际挂载状态选择已冻结的逻辑文件/NVS 采集，或不挂载文件系统的原始介质读取。
2. 明确原始介质范围、物理/解密字节语义、读取错误、来源身份及固件版本；不能把部分分区
   或逻辑对象声称为完整可恢复设备备份。NVS/完整 Flash 可能包含凭据，须有明确设备确认和私有接收存储。
3. 使用有界背压、取消、期限、帧身份与交付 ACK 的实体传输；接收完整且独立重算成功才记录交付完成。
   MAC/ELF 字符串 pin 仍不等于密码学设备认证。
4. 失败或重启保留原始字节和未完成状态；源证据、云端认证对账与受控维修/回滚保持独立。
5. 在可恢复设备上完成未挂载、已挂载、断线、慢接收、取消、重启和断电 HIL。

本批只修正启动挂载判定并建立回归，不接设备、不读取原始介质、不部署、不刷机，也不授权数据维修。
逻辑导出实体入口、原始介质路径和候选安装/回滚仍需继续实现。
