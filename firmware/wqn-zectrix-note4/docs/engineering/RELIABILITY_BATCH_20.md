## 问题与处理

第十九批额外探针已复现：本地成功接受 A 后，读取 A 时只拒绝一次 cJSON 分配，
再提交 B 返回成功；整理将 A 当作坏记录删除，主文件与备份均不再保有 A。
这证明代码失败处理存在数据损失路径，不表示已经发生设备现场事故。

cJSON 的空解析结果同时表示语法错误与分配失败；所用 IDF 的 malloc 包装也不提供
可用于此处可靠区分的 errno。每次操作临时替换全局 cJSON allocator 会影响其他任务，
因此本批不采用全局 hook 或依赖诊断开关的 heap 回调。

内部解码结果现在分为有效、已确认坏帧、暂不可解码。正常成功解析路径保持现状；
仅在解析失败后运行无堆分配、无递归的语法探针，使用最多 33 个容器状态槽，
匹配当前 SDK 的 BOM、空白、字符串转义/Unicode 和兼容数字语法。完整且可能有效的
JSON 返回暂不可解码，不能因资源不足而当作坏帧清理；探针不是另一套业务解码器。
语义无效但语法完整的行在解析资源恢复后仍由原字段校验决定是否清理。

`ReadOutboxLines`、新增/幂等查重、Peek、ACK/隔离、Snapshot、挂起查找六处入口
均传播 `ESP_ERR_NO_MEM`，在后续写入、整理或状态成功确认前结束。读入的部分结果
不用于发布。真正坏帧、NUL、超长行与残尾保留原有有界恢复策略；正常 journal 格式、
发布顺序与 request ID 幂等语义不变。既有中断发布的备份恢复仍可在读取前执行。

这种处理优先保全：不能证明为坏帧时返回可重试错误，而不是猜测记录可以删除。
后续升级 cJSON 时须重跑兼容语法及分配故障回归，不能只依赖一次正常解析测试。
本批保护 cJSON 分配失败，不声称已消除所有 STL/系统分配失败或物理介质风险。
