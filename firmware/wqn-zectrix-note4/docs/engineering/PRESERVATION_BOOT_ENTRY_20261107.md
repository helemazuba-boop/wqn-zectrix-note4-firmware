# R-08 预初始化保全入口

正常启动后遇到 SEQUENCE_GAP 的设备也需要能导出原始介质。继续常规启动会执行
NVS 初始化、schema/重置意图处理、SPIFFS 挂载及同步；这些步骤可能改写待保全数据。
当前入口在这些步骤之前分流，不在存活的同步/持久化任务间强行切换模式。

## 使用方法

适用配置是 Note4 ESP32-S3 / ai-local / EPD UI。先结束当前学习、录音或保存操作。
在一次重新上电或用户主动复位之前按住**上翻页键**，并保持至少 3 秒，出现“数据保全”
后松开。已有串口监视器的 F2 可由用户主动复位；这里没有增加自动复位命令。
普通深睡唤醒不检查此手势，需要一次真正的重新启动。

不要按住确认键复位：确认键 GPIO0 参与 ESP32-S3 启动绑带，可能进入 ROM 下载模式。
入口只读取上键 GPIO39，不更改已有按键 ISR/采样流程，不把下键开机动作当维护意图。
未按上键的常规启动立即继续，不增加 3 秒等待。

“数据保全”页提供“保全原始镜像到电脑”和“重启正常启动”。选择镜像后，仍必须
等待新警告呈现，再以一次新的确认按下/松开保持至少 2 秒；开机手势不能授权导出。
敏感范围还需电脑 `--sensitive-main-flash`，MAC 与 ELF 摘要 pin 绑定。
电脑接收工具、落盘 ACK 和离线校验见 RECOVERY_DEVICE_EXPORT_20261107.md。

本模式不初始化 NVS、不挂载 SPIFFS、不检查业务 schema，也不处理先前的清除意图；
所以只提供原始镜像，不提供逻辑证据、NVS 诊断或清除操作。取消导出警告返回保全页，
不会进入带逻辑导出选项的故障恢复子菜单。任务与采集器也会拒绝越过该范围的调用。

“重启正常启动”会在新的确认后恢复常规流程，可能执行此前已经确认保存的清除请求。
保全不会撤销该请求。当前 RAM 中尚未保存的操作也不会跨用户复位保留。
工具不自动格式化、回放、修复或取消任何持久化意图。

## 启动顺序和约束

1. HAL 设置安全引脚，上键输入已启用上拉。
2. 在自动 light sleep 和普通按键采样任务启动前检查上键。只在开始时为低才轮询。
   连续保持至少 3 秒才请求保全；期间释放则正常继续。
3. 采样无效、计时倒退/异常或 512 次采样后仍无法结束，均阻止常规存储启动。
   512 次是迭代上限，不是最坏调度延迟保证。上键卡低会进入保全，不会自动清除。
4. 完成不依赖业务存储的电源/睡眠锁准备，然后发布一次性的 preservation_only 上下文。
   该上下文只单向发布；后续尝试改回普通恢复模式会被拒绝。
5. 直接进入保全 UI，跳过 EnsureStorageSchema、InitStorage、PrepareSyncServiceAtBoot、
   OTA app-valid 确认，以及音频/AI/网络/同步/普通 UI 和 PowerCoordinator 的启动。
6. 首次用户确认导出才启动维护 StorageService owner。电脑 READY 前仍不采集原始数据。
   检查/清除/逻辑导出在 owner、export worker 与逻辑采集器边界被拒绝。

该声明只覆盖应用内的业务介质访问。ROM/bootloader 可能在 app_main 前更新 OTA 状态；
原始镜像仍不声称是启动前快照、原子快照或完整设备备份。保全入口刻意不写 OTA
app-valid 标记；若新装 OTA 镜像仍处于待确认状态，后续重启行为需要另行验收。
电源/I2C/EPD 硬件故障仍可能阻止界面启动；采样错误时不会因此放行业务启动。

## 本地验证与尚待验收

- test_storage_preservation_boot.py 编译真实 selector，通过 reset/GPIO/timer 端口覆盖
  未按键、3 秒保持、提前释放、深睡唤醒、无效读数、倒退/负数/停滞时钟与空参数；
  100/1000 Hz 均执行。缩短保持或放开深睡检查的负对照必须被语义断言检出。
- test_sync_boot_recovery.py 编译 main.cpp 的真实启动体和两个恢复分支，保留 SDK/服务
  边界为端口；跨 WiFi/Agent 三种配置验证分流早于 schema/重置、存储、同步和 OTA 确认。
  将分流后移或忽略采样错误的变异必须被检出，不能因异常崩溃算通过。
- test_storage_recovery.py 覆盖只读模式的菜单、独立的新确认、警告取消返回、owner
  拒绝检查/清除/逻辑请求、允许原始请求，以及精确终态 ACK。
- test_storage_evidence_capture.py 验证即使外部端口声称已经挂载，手动保全上下文也
  不能使逻辑采集器读取文件/NVS。test_evidence_transfer.py 验证真实 worker 的原始
  交付，以及逻辑请求在分配传输通道之前被拒绝。
- M8、profile、UI 入口栈和完整鲁棒性门禁仍是提交前要求。变更 UI 签名后，静态栈
  检查必须针对 RunStorageRecoveryUi(int, bool) 的真实编译入口。

上述均是主机/构建证据。实体 GPIO39 极性与开机时序、真实深睡按键体验、上键卡低、
USB 复位、待确认 OTA、加密 Flash、16 MiB 镜像、磁盘/拔插/取消/断电、内部堆与真实
栈余量仍待 HIL 和独立审查。可信来源、认证核对、受控安装/回滚仍未完成，R-08 保持开放。
