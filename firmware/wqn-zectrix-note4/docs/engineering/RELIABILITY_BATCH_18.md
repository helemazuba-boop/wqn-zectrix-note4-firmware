## 确认的问题与最小修复

Save*PackManifestRaw 原本检查顶层/行对象创建和最终 Print 的失败，但许多
cJSON_AddString/Number/Bool/Null、AddItemToObject 的返回值未检查。cJSON 字段构造
既分配节点，也可能分配字符串值和 key；其中一次失败后，后续分配可以恢复，Print
仍可能成功。此时原逻辑会写入并发布一个缺字段 JSON，返回 ESP_OK，原主清单已转为
备份。只把“此后所有分配一直失败”注入为测试，会因 Print 也失败而掩盖该路径。

定向把故障点移到必需字段的分配后，三个旧实现均返回 ESP_OK，主文件已改变且
备份已轮换；新主文件分别被对应生产解析器拒绝，结果均为 INVALID_RESPONSE
（264）。探针只改变测试驱动的输入形状/失败序号，未改变生产函数，记录与驱动
随镜像归档。该复现证明错误发布决策，不证明现场已经发生相同事故。

本批在序列化阶段检查每个字段和容器结果。嵌套 object/array 使用 cJSON 自身的
AddObject/ArrayToObject，其挂接失败会清理未拥有的子节点；数组行先确认挂接，失败
显式删除未挂接行。后续字段失败删除 root，释放全部已挂接后代，返回 ESP_ERR_NO_MEM。
仅完整构造并 Print 成功后才打开 manifest 临时文件，原持久写、备份/主文件 rename
与第十七批淘汰策略继续执行。

没有新增磁盘格式、任务、锁或常驻状态；错误类型使用原 ESP_ERR_NO_MEM，调用者
沿用现有保存失败/重试流程。检查的是 cJSON 所报告的构造失败，不保证任意 C++ new、
VFS、Flash 或掉电故障都能恢复；整轮跨 lane manifest 安装隔离仍不在本批范围。
